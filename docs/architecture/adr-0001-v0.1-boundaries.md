# ADR-0001: v0.1 offline architecture boundaries and engineering constraints

- **Status:** accepted
- **Date:** 2026-07-26
- **Issue:** [#2](https://github.com/khvedela/wirelens/issues/2)
- **Parent epic:** [#1](https://github.com/khvedela/wirelens/issues/1)

## Context

WireLens v0.1 must analyze PCAP/PCAPNG captures fully offline with clear responsibility boundaries across React, Web Worker, Rust/Wasm, and platform-neutral Rust crates. The decision must preserve privacy-first local processing, keep expensive parsing/filtering off the browser main thread, and allow independent implementation/testing of core parsing and analysis.

## Decision summary

WireLens v0.1 adopts a **worker-centered, handle/index-based Wasm boundary**:

1. React never parses capture bytes and never calls protocol logic directly.
2. The Web Worker owns import lifecycle, execution orchestration, cancellation, and query dispatch.
3. Rust `packet-core` and dependent analysis crates remain platform-neutral and own parsing/indexing/filter execution.
4. Wasm adapter exposes opaque dataset/query handles and returns batched typed-array-backed results (plus small structured metadata).
5. Browser main thread receives presentation-ready slices only; no full-capture JSON materialization is allowed.

## Responsibilities by runtime

### Browser main thread (React + TypeScript)

- File selection UX and user intent collection.
- Rendering packet table, filter controls, packet detail panes, and progress states.
- Sending commands to worker and rendering worker responses.
- Optional local persistence UX (explicit opt-in only).

Must not:

- Parse packet bytes.
- Execute full-capture filtering/indexing.
- Block on heavy loops.

### Web Worker (TypeScript boundary + orchestration)

- Receive file bytes from main thread and transfer ownership to Wasm pipeline.
- Create/import dataset handles and maintain request/response correlation.
- Execute cancellation, backpressure, and progress reporting.
- Translate UI queries into stable Wasm API calls.
- Return bounded result batches and typed-array views to main thread.

### Rust/Wasm adapter

- Safe, explicit ABI between worker and platform-neutral Rust crates.
- Handle registry lifecycle for imported captures, indexes, and query contexts.
- Batching/pagination primitives for packet rows and field views.
- Structured error categories suitable for UI handling.

### Platform-neutral Rust crates (no browser/Wasm dependency)

- `packet-core`: capture ingestion primitives, packet buffer ownership model, parse cursors, normalized packet model.
- `protocol-decoders`: link/network/transport/DNS decoding and malformed/truncated safety behavior.
- `flow-engine`: flow reconstruction, indexes, and lookup structures.
- `analysis-engine`: filter execution and evidence-linked summaries.

Must remain reusable by future native CLI/agent targets.

### Native component (deferred from v0.1)

- No native runtime dependency for v0.1 offline capture analysis.
- Future live-capture agent remains optional and must consume the same platform-neutral Rust core.

## Package and crate boundary rules

- `apps/web` depends on worker protocol types, never on protocol parser internals.
- Worker depends on Wasm adapter bindings, never on Rust core internals directly.
- `wasm-adapter` depends on `analysis-engine`/`flow-engine`/`protocol-decoders`/`packet-core`.
- `packet-core` must not depend on Wasm/web/React/DOM APIs.
- Dependency direction is inward toward platform-neutral Rust crates.

## Data ownership and boundary contracts

### Ownership model

1. **Import start:** Browser obtains `File` and streams/reads bytes for worker handoff.
2. **Transfer to worker:** Browser transfers `ArrayBuffer` ownership (transfer list) to avoid clone.
3. **Wasm ingest:** Worker passes byte view into Wasm import API; Rust allocates owned capture storage for datasets that outlive call boundaries.
4. **Query operations:** UI sends query params only. Worker routes request by `dataset_handle` and optional `query_handle`.
5. **Query results:** Rust returns bounded batches: packet ids/ranges, offsets, timestamps, field descriptors, and evidence references via typed arrays + compact metadata.
6. **Presentation:** Main thread renders slices and requests additional batches on demand.

### Copy/allocation points (expected and controlled)

- One transfer ownership change browser -> worker (no duplicate copy target behavior).
- One Rust-side owned allocation for persisted dataset/index memory.
- Bounded per-query batch allocations for result payloads.
- No whole-capture JSON expansion across any boundary.

### Cancellation and failure behavior

- Every worker request includes `request_id` and optional `cancel_token`.
- Worker supports cooperative cancellation for long imports/filters.
- Rust operations check cancellation points between chunks/batches.
- On cancellation, partial progress is reported and temporary query allocations are reclaimed.
- Parse failures are packet-scoped when possible; malformed records produce structured diagnostics, not panics.

## Required experiment: two boundary designs

## Design A (chosen): worker-centered handle/index API

Flow sketch:

- **Import:** Main thread transfers bytes -> worker -> Wasm `import_capture` -> returns `dataset_handle` and progress events.
- **Cancellation:** UI sends cancel for `request_id`; worker forwards cancel to Wasm context; Rust exits at chunk boundary and returns cancelled status.
- **Packet selection:** UI requests packet page by handle + range; worker returns typed arrays for row fields.
- **Filter execution:** UI submits filter expression; worker starts query handle, streams batch results incrementally.

Pros:

- Strong ownership clarity and low-copy behavior.
- Scales to large captures via paging/batching.
- Keeps expensive work off main thread.
- Reusable platform-neutral Rust core for future native targets.

Cons:

- Requires careful handle lifecycle management.
- Requires explicit cancellation checkpoints in Rust.

## Design B (rejected for v0.1): batched structured object transfer

Flow sketch:

- **Import:** Wasm parses and emits large structured JS objects per chunk.
- **Cancellation:** Worker stops awaiting additional chunks; Rust may continue until emission boundary.
- **Packet selection:** Main thread queries in-memory JS object graphs.
- **Filter execution:** Worker or main thread re-filters structured objects.

Why rejected:

- Higher allocation/GC pressure and object churn.
- Greater risk of accidental full-capture duplication.
- Weaker ownership guarantees across boundaries.
- Harder to guarantee latency/memory budgets for large captures.

## Security and privacy constraints (normative)

1. Offline mode must not upload packet bytes or decoded payloads.
2. Network access from analysis path is disabled by design; no remote dependency required to inspect captures.
3. Captures are hostile input: no panic-on-parse, no unchecked indexing, bounded allocation growth, and explicit malformed/truncated handling.
4. UI/export text must distinguish observation from inference and preserve evidence references.
5. Raw capture persistence/export is explicit user action with warning; derived summaries are preferred.
6. Logs/telemetry must exclude packet payload bytes and sensitive decoded fields.

## Measurable v0.1 success criteria

### Privacy

- **P1:** During offline analysis, zero network requests contain capture bytes or decoded payloads.
- **P2:** Default workflow completes without writing raw captures to persistent browser storage unless user opts in.

### Latency and responsiveness

- **L1:** For a small capture (<= 10 MB), first packet table page is renderable within 1 second of import completion on a reference laptop.
- **L2:** For a large capture (>= 500 MB), UI main thread long tasks over 50 ms attributable to parsing/filtering are zero.
- **L3:** Filter cancellation acknowledgement reaches UI within 200 ms median.

### Throughput

- **T1:** Large-capture import pipeline sustains >= 50 MB/s effective ingest+index rate on reference hardware.
- **T2:** Filter execution returns first result batch within 1 second for indexed header-field predicates on the same dataset.

### Memory

- **M1:** Peak browser+worker+Wasm memory remains <= 2.5x input capture size for the large-capture path.
- **M2:** Query result transfers are batch-limited; no single UI response payload exceeds 8 MB.

### Correctness and robustness

- **C1:** Malformed/truncated packet records produce structured errors and continue best-effort parsing when safe.
- **C2:** Every analysis summary references supporting packet ids/ranges.

## Consequences

- Workspace and package implementation issues must conform to this dependency direction and ownership model.
- Wasm API design work should focus on handle lifecycle, paging, cancellation, and typed-array contracts.
- Performance and memory benchmarks must validate P/L/T/M criteria on both small and large captures.
- Any proposal that introduces main-thread parsing or full-capture structured transfer must be raised as a new ADR.

## Out of scope for this ADR

- Final crate/library selection.
- Full filter language specification.
- Live capture/eBPF implementation details.
- UI component library choice.
